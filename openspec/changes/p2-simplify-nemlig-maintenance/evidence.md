- Luna verified current knownProducts is a per-client Map capped at 1,000 entries. Writes refresh insertion order; reads do not. getFreshProduct bypasses it, and hosted clients are isolated by principal/credential generation. The ordered discovery pool is eight lines, concurrency three. No observed defect justifies replacing these with a scheduler or cache package.
- Isolated npm metadata/package inspection: lru-cache 11.5.2 is BlueOak-1.0.0, Node 20 or >=22, zero runtime dependencies, 2,737,736 unpacked bytes / 579,936 compressed. Pacer 0.22.0 is MIT, Node >=18, 1,314,758 unpacked / 192,735 compressed, plus TanStack Store and Devtools dependencies. Pacer Lite 0.2.2 is MIT, Node >=18, zero runtime dependencies, 267,008 unpacked / 43,984 compressed. Neither Pacer variant exports LRU/cache APIs. No packages were installed in the repository by this investigation.
- Direct isolated lru-cache behavior check showed get promotes read recency while peek does not. Adopting ordinary LRU get would change current eviction semantics; a drop-in claim would be false. Fresh mutation-adjacent lookup must remain provider-backed regardless of any later choice.
- Separate opportunity, not implemented here: concurrent duplicate selected-product IDs may repeat an uncached exact read. No measured user impact yet. A fake-provider characterization should compare request count/latency/heap for duplicate misses and hot reads before selecting in-flight coalescing or an LRU policy. Never coalesce getFreshProduct with cached planning reads. Keep current safeguards and do not add a dependency solely for module count.
