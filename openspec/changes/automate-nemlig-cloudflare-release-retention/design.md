## Decisions

- Keep workflow_run trust separation and exact per-SHA CI provenance. Use the native Actions queue, accept a queued SHA while it remains in main history, and refuse to overwrite any already-deployed descendant. Do not add custom queue-overflow recovery.
- Keep production mutation behind one non-canceling production concurrency group and the existing cross-host operation lease while any code path needs it.
- Record accepted-image identity and order durably only after exact runtime acceptance. Reuse the existing GitHub state-ref persistence mechanism with strict compare-and-write behavior; do not place credentials or shopping data in it.
- Determine tag-to-digest, creation/order, Worker-version references, and deletion semantics using Wrangler 4.127.1 and read-only production evidence. Incomplete pagination, stale operation ownership, uncertain active/recovery references, and untracked digests always stop deletion. Historical accepted order may be reconstructed only from exact, durable acceptance artifacts for the matching full commit and digest.
- Set ten distinct accepted image digests as the default retained window. Protect active, rolling, current, unresolved recovery, uncertain and explicit held digests beyond that count. Delete safe candidates sequentially after each accepted release, re-reading inventory/references and revalidating the tag before each delete; there is no count-based per-run deletion cap.
- Gate cleanup after verified deployment acceptance and durable report/ledger write. Cleanup failure is a separate outcome: it neither rolls back a healthy release nor changes the kill switch.
- Retention claims the existing `codex-lock/nemlig-production` ref with compare-and-create/fast-forward semantics, fencing both hosted and supervised local deployments. Each exact tag deletion has a durable in-flight intent before the provider request; a completed prior GitHub run may be reclaimed only by a fresh retention operation that resolves the tag from a complete inventory. A deployment-owned, malformed, active, or uncertain lease is never taken over.
- Each accepted release performs two same-run inventory/reference reads before cleanup; they must produce the same fingerprint. Cleanup then starts in that post-acceptance job, and every destructive step still revalidates the current lease and references.
- Cleanup has no recurring schedule or enable flag. If a runner stops during deletion, an operator explicitly resumes that accepted commit through the existing protected workflow; uncertain tag outcomes remain held rather than retried.
- Acceptance failures retain a fixed stage category in the public-safe journal; raw command output, response content, and credentials are never copied into diagnostics.
- Keep Worker versions/deployments, secrets, Durable Object state, Container applications, foreign repositories and basket/order/payment/delivery state out of deletion scope.
- Worker-version cleanup runs only after image retention succeeds, acquires the same shared production lease used by deployment and image retention, derives recovery references from the exact release journal, validates Cloudflare pagination cardinality, and persists a bounded report before and after each deletion. An uncertain Worker deletion keeps the lease and requires the explicit reviewed `resume_worker_retention` path to reconcile the pending version; it is never retried automatically.
- Simplify local locks, remote journals, artifacts and manual finalization only after failure-state tests prove that remaining GitHub/Cloudflare state is sufficient for runner loss before mutation, ambiguous transition, post-readback/pre-cleanup loss, and interrupted deletion.

Failure-boundary review: pre-mutation rejection is covered by source/CI/lease tests; cancellation during deployment and a late provider success retain the lease and suppress follow-up mutation; acceptance artifact failure prevents routine finalization and the retention job requires successful deploy plus that artifact; interrupted tag deletion is represented by a durable in-flight intent and resumes only from a fresh exact-tag inventory. The obsolete cutover state and manual dispatch modes are removed because routine release tests no longer require them. The deployment journal, shared lease, and accepted-image ledger remain: active production recovery evidence and uncertain deletes make those records non-redundant.

## Failure handling and migration

The implementation offers a reproducible read-only plan and a pure planner. The post-acceptance path requires two stable same-run snapshots before deletion. If Cloudflare cannot expose authoritative order or references, retain the affected image indefinitely and report the reason. A deletion timeout is uncertain: stop, persist the partial report, re-inventory on an explicit resume, and never blindly retry.

Deploy uses the configured production variables as source of truth, explicitly including the credential-key version and live values the contract permits to carry forward. Wrangler must preserve encrypted secrets. The unused minimal-auth variable is removed by replacement with the declared config and verified absent; no hidden runtime behavior is retained.

No new runtime dependency, Cloudflare resource, external scheduled service, or extra Container is intended. Image cleanup runs only after each accepted deployment; there is no cleanup cron or custom deployment catch-up schedule. Workflow checks, a durable accepted-image ledger, registry adapter, pure planner, focused operation tests, docs, exact-main CI, and read-only acceptance constitute the implementation boundary.

## Risks

- A Worker version can still be visible after its image is removed; preserve audit records and state clearly that rollback is supported only while the corresponding image is retained.
- A short tag can alias another digest or change between listing and deletion; resolve and revalidate immutable digest identity immediately before every deletion.
- Registry data may not expose trustworthy build time; block deletion where acceptance order cannot be proved.
- A missing/corrupt ledger loses historical classification; fail closed, hold images, and require explicit reconciliation rather than reconstructing from tags alone.
- GitHub may reject excess pending workflow runs at its native queue cap; no custom catch-up infrastructure is justified for this rare platform failure. A later eligible merge triggers the normal path.
- Broad workflow permissions or secret inheritance could expose provider credentials to PR code; keep credentials solely in the protected deploy job and tests that inspect workflow permissions.
- Changing keep_vars behavior could remove required configuration if allow-lists are incomplete; characterize all current variable names/types, explicitly allow required values, preserve secrets, and require post-deploy exact config readback.
