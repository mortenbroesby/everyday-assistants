# Nemlig operation journal compatibility (issue #324)

This is the Step 4 implementation record for [#319](https://github.com/mortenbroesby/everyday-assistants/issues/319), stacked after the [#323 review contract PR](https://github.com/mortenbroesby/everyday-assistants/pull/330). The [architecture baseline](nemlig-architecture-refactor-baseline.md) and [backend retirement record](nemlig-backend-retirement.md) establish reachability; this note records the journal boundary. It is source and synthetic-test evidence, not a claim about current production records or live Nemlig behavior.

## Operation inventory and decision

| Current direct Submit: `ProductReviewService.submitDirectBasket`, `direct-basket-submit:<draftId>`, kind `submit` | Exact account, generation, reviewed product IDs/quantities and basket baseline. `read` fences replay; `write` then atomic `claim` precedes one provider bulk add; `complete` follows provider readback. | Completed receipts have a two-hour `completedUntil`; unresolved attempts remain. The process-local draft has its own terminal guard, including after receipt expiry. Keep. |
| Current optional whole-basket Save: `saveCurrentBasketAsShoppingList`, `direct-basket-save:<draftId>`, kind `basket-save` | Exact account, generation, current basket items/baseline. `read` fences replay; `write` and atomic `claim` precede one provider request; `complete` follows acknowledgement. The provider does not return a reliable list ID. | Completed receipts have the same two-hour limit; unresolved attempts remain. Keep. |
| Historical native-list create: retired service path, kind `save`, operation ID was the draft ID | `createAttempted`, optional `listId` and `progress` could mark partial or uncertain provider work. Storage/callback still read and preserve these fields; no current service produces them. | An unclaimed, ID-less intent expires after 24 hours. Claimed/uncertain work stays fenced; completed records follow their existing limit. Keep historical parsing and storage behavior. |
| Historical native-list edit: retired service path, `native-list-update:<listId>`, kind `update` | `listId`, items, baseline and attempt/progress fields. No current service producer; storage/callback still accept and read it. | Unresolved work has no automatic expiry. Keep; production receipt population is unknown. |
| Historical native-list transfer: retired service path, `native-list-submit:<listId>`, kind `submit` | `listId`, `dispatchAttempted`, baseline and optional cleanup status/warning. No current service producer; storage/callback still accept and read it. | Completed native submissions without `completedUntil` remain fenced. Keep; do not reuse a direct receipt rule for them. |

The application journal port now accepts only current direct intents and omits its unused `release` adapter. The `review-operation-release` callback and storage branch remain for historical command compatibility. This does **not** imply release is generally safe after a claim; it must not be used for uncertain provider writes. Historical `ReviewOperation` fields remain in the durable reader and callback schema. No persisted record, key, command or retention rule is migrated or deleted.

The capacity code arises while writing the intent, before this attempt's provider dispatch. Its shared callback/MCP response says no write was sent for **this attempt** and cautions that an earlier attempt may still be uncertain. A completion failure after dispatch takes the separate generic storage/uncertainty path, not the capacity code. The 429 status and machine error code remain stable; the viewer conservatively treats the capacity response as uncertain rather than authorizing a replay.

## Safety and rollback boundary

The Worker admits an authenticated principal and grants a short-lived callback capability. The Container sends a `review-operation-*` command to `local-basket-state.internal/inventory`; the callback resolves the owner from that capability, rejects credential-bearing/invalid/oversized requests, and reaches `OwnerLocalBasketStorage`. Its `NEMLIG_LOCAL_BASKET_STORAGE` binding and migration tags remain unchanged. The owner record stays under `owner-review-operation-index`; its claim, read, write, completion and pruning run inside the existing Durable Object concurrency/transaction boundary. Stable wire command names, error code `LOCAL_BASKET_OPERATION_CAPACITY`, and the callback route/headers remain unchanged.

`claim` is the only dispatch authority. A generation mismatch, attempted/completed claim, conflicting account/payload, failed journal write, capacity failure or unavailable callback must stop provider dispatch. Once a claim might have preceded an external request, an absent/failed response is uncertain and must not be retried. Completion and basket readback are separate evidence; neither a passed synthetic test nor a renamed type proves the live provider outcome. Completed direct receipts are bounded because their process-local drafts cannot be rehydrated after restart; a historical native submission has a different lifetime and cannot inherit that expiry.

The old `expireOwnerLocalBasketInventory` alarm remains a no-op because deployed objects may still have pending alarms and historical storage ownership is unknown. Removing the method, changing `replaceCompleted`, deleting historical fields/commands, or shortening retained receipts requires a separately reviewed migration and rollback decision based on real record evidence. A rollback to the earlier service can still read the unchanged serialized shape.

## Verification boundary

Synthetic storage tests characterize owner isolation, exact account/payload/generation conflicts, claim fencing, direct and historical retention, capacity and old receipt fields. Callback/capability tests characterize owner derivation, rejected credentials, malformed input and capability lifetime. Product-review tests also inject a completion outage after dispatch and verify that the pending receipt prevents a second write after service restart. MCP/HTTP and UI smoke tests characterize one provider dispatch, readback, replay/uncertainty and current contracts. Exact commands/results belong in the PR and issue handoff. No production Durable Object contents or live provider writes were inspected for this change.

A separate credential-free local Wrangler 4.127.1 simulation exercised the actual `mutateOwnerLocalBasketInventory` function inside a SQLite Durable Object and `blockConcurrencyWhile`, using an isolated `/tmp` state directory and synthetic records. Eight simultaneous claims for one direct Submit produced exactly one `true`; a different owner and changed payload were rejected without altering the claimed record. After stopping and restarting Wrangler with the same local state, the attempted receipt remained, a second claim returned `false`, completion persisted, and a post-completion claim also returned `false`. This checks the local runtime transaction/restart boundary; it does not inspect production records, prove deployment compatibility, or replace the existing capability and provider-flow tests.
